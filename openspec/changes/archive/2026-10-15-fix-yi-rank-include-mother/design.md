# Design

## Context

动机见 `proposal.md - Why`，这里只记实现层面必须知道的三件事。

**1. 错在哪一行。** `kinship.js` 的 `sibGroup(idx, id, anchorId, step)` 在 `step === 'Z'` 且锚点落在群体里时把锚点剔出序列。这条规则为 `Z`（**我的姐妹**）而写 —— 那个场景锚点是「我」，我的姐妹不该把我算进姐妹序列。但 `M Z` / `F Z` 走的也是 `step === 'Z'`，而它们的锚点是 `nodes[subjectIdx - 1]` = **参照长辈本人**（妈妈 / 爸爸），于是妈妈被剔掉，序位整体前移一位。排查入口：`finalize` 里 `anchorId = nodes[subjectIdx - 1]`、`step = symbols[subjectIdx - 1]`。

**2. 「小」化从来没能在这份数据上生效。** `isYoungestSmaller` 只比出生年（`yearOf`），任何一环缺失即返回 false。本机 `我的家族` 谱 178 人中仅 2 人填了出生年（王寄阳 1989、王寄林 1997），外婆家七个孩子与父母全部为空 → 该分支在这本谱上恒为 false。

**3. 排行值（`order`）在这本谱里是混排连续号**（0..6，跨男女），与 memory 里「同性连续编号」的旧假设不符。这意味着**同性子序列的相对顺序仍然可信**，可以拿它比大小；只有跨性别的绝对值（如「order 9 是第五个儿子」）才是 `所见即所得` 的产物。`order` 语义：**同一对父母下的出生序**，跨家庭不可比。

## Goals / Non-Goals

**Goals:**
- 排行序位对同一个人跨视角稳定（见 specs 的「排行称呼与视角无关」）
- 「小」化在本机这份无出生年数据上真正生效
- 「小」化的候选池口径与排行主体解耦，两处改动互不干扰

**Non-Goals（用户明确排除）:**
- 舅舅一侧不动：妈妈是女儿，进不了儿子序列，男性仍直取 `order`
- 长幼判定本身（`F B` 伯/叔、`W Z`/`H Z` 大姨子/小姨子等选词）继续以出生年优先 —— 用户同意下一轮再议
- 不新增数据字段，不做数据迁移

## Decisions

### D1 剔除条件按「锚点是不是我」判定，而不是按步符号

`step === 'Z'` 无法区分「我的姐妹」（锚点=我）与「妈妈的姐妹」（锚点=妈妈），必须换成位置判定：**只有锚点等于 `nodes[0]`（视角人物自己）时才剔除**。

- 备选①：按路径字符串区分（`MZ` / `FZ` 不剔、裸 `Z` 剔）—— 规则表里 `W F Z` / `H M Z` 这类前缀会让字符串判断到处漏分支。
- 备选②：给 `sibGroup` 多传一个 `isMySiblings` 标志 —— 多一个入参、多一处可能传错，收益为零。
- 结论：位置判定一处即可，`plain Z`（我的姐妹）与 `M Z`（妈妈的姐妹）同时正确。

### D2 「小」化的候选池另立一个序列，不复用 `sibGroup`

`sibGroup` 承担两个不同语义的职责：排行要**同性**子序列（舅姨各排各的），「小」化要**全体同胞**（叔姑抢同一个「小」）。若给 `sibGroup` 加性别开关，一个参数要同时影响两条口径，改一处坏一处。

- 新增一个只服务于 `isYoungestSmaller` 的分组：**参照长辈的全部同胞 + 参照长辈本人**，按 `order` 升序，不筛性别。
- 「小」化只在这个序列上判：序位最大且 `order` 大于参照长辈 → 小X；否则照报排行。
- 收益：排行的同性重数与小化的全体候选各自独立，以后再调一边不会连带另一边。

### D3 「小」化彻底改用 `order`，出生年只留给长幼判定

`isYoungestSmaller` 改为纯 `order` 比较，函数签名从「读 nodes[1] 的出生年」变成「读参照长辈的 `order`」。`yearOf` / `compareAge` 仍由 `judgeAge` 使用，不动。

- 理由（用户）：修家谱的人知道排行、未必知道年龄；且存在辈分大年龄小的人，年份本身不可靠。
- 代价：录错排行就会叫错「小」。见 Risks。

### D4 排行值缺失时整组退回照报排行（推论，非用户原话）

用户说的是「**断号**按记录里最后一个算」，那说的是 `0 / 2 / 5` 这种有值但跳号的情形。`order` **整格为空**是另一回事 —— 没有值就没有大小可比。规则：候选池中任一人 `order` 为空 → 本次不启用「小」，全体照报排行（延续 2026-10-10「宁可叫四舅也不猜一个小舅」的保守口径）。

### D5 裸 `B` / `Z`（我的兄弟姐妹）的分侧逻辑原样保留

`finalize` 里那段「按称呼类型分组数、某一侧只有一人就不报数」（`:517`–`:572`）不参与本次改动：它处理的是「我」与同胞，锚点是「我」，D1 的新条件对它等价于旧行为，回归时只需确认既有断言仍绿。

### D6 注释纠错随代码一起改

- `rules.js` 的 `Rule` 类型 JSDOC 写着 `small`「排行第 4 位起、又是那批人里最年轻的，才用这个称呼」—— **这个门槛用户 2026-10-10 已否掉**，从来没有第几位门槛，是错误注释。
- `kinship.js` `:501` 注释「锚点 = 主语的父亲（再上一级那个人）」不准确：`M Z` 的锚点是妈妈，不是外婆。改为「路径上主语的前一个人；对 `M Z` 而言是参照长辈本人」。

## Risks / Trade-offs

- **[舅舅排在最末 → 姨一个都叫不到「小」]** → 用户已确认接受。口径是「爸妈全体同胞里最小的那一个」，不是「姨里最小的」。缓解：写进 specs 的场景，用户日后要改就是改这条口径，不是改代码。
- **[叔叔与姑姑抢同一个「小」]** → 爷爷家最小的是女儿时，族里就没人叫「小叔」。用户 2026-10-15 确认「一起」。口语上本就合理（那批孩子里最小的那个），但与旧测试期望冲突（`tests/run.js:1013` 四叔 → 五叔）。
- **[姐妹 ≥ 6 人时出现「五姨」]** → 那是实打实的女儿序，不是 2026-10-10 说的「把舅舅的序号算进去」。真实家庭里最年轻那位通常被叫小姨，所以实际最多露到「五姨」。
- **[排行填错 / 断号 → 「小」叫错人]** → 用户明确接受「按记录里最后一个算」。缓解：specs 场景写死「0 / 2 / 5 → 排行 5 那位叫小X」，并在 `note` 保留规范称谓备查。
- **[序位在妈妈的孩子界面上「看起来跳号」]** → 长女是长女、二女是二女，长女的孩子们叫二姨「二姨」而不是「一姨」。这是妈妈占号的结果，不是 bug；设计文档与 specs「视角无关」那条一起说明，避免以后被当成 bug 报回来。
- **[岳家侧（`W M Z` / `H F Z` 等）行为随之变化]** → 用户要求「一起」，语义与自家侧完全一致。回归时需覆盖 `W` / `H` 三边对称（memory 铁律：改称谓必须三边同步）。
- **本仓库没有 git** → 改动前必须 `Copy-Item` 备份 `kinship.js` / `rules.js` / `tests/run.js` 到 `%TEMP%`，出错好回滚。

## Migration Plan

1. 备份三个文件到 `%TEMP%`（本仓库无 git，这是唯一的回滚手段）
2. 改 `sibGroup` 的剔除条件（D1）、新增全体同胞分组（D2）、重写 `isYoungestSmaller`（D3 + D4）
3. 改 `rules.js` / `kinship.js` 的错误注释（D6）
4. 更新 `tests/run.js` 四处断言：`:815`、`:863`、`:988`、`:1024`（外加 `:1013` 四叔 → 五叔这条随 D2 的口径变化）
5. 跑 `node app/tests/run.js` 全绿；再用只读探针（`sql.js` 读 `数据/books/book-mv247k0n-bo0l/genogram.db` + 直接 `deriveKinship`）核对本机四组期望：李书香=二姨、李书菊=小姨、王寄林→李书敏=大姨、王寄林→李书香=二姨
6. `npm start` 目视验收卡片上的称谓（不打包）

回滚：把三个备份文件拷回即可，无数据迁移、无 schema 变更。

- 长幼判定（伯/叔、大舅子/小姨子一类选词）是否也改成排行优先？用户 2026-10-15 明确「先不动」，留到下一轮；它不改变本变更的任何 spec。
