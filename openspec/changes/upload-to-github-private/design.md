# Design

> 动机见 proposal.md - Why。此处只记做方案需要的现状事实与决策理由。

## Context

**工具链现状（2026-10-21 实测）**：

- git 2.56 已装，全局身份已配（`user.name` / `user.email` 均已设置，提交作者即真实身份）。
- `gh` CLI 2.100 已装，**未登录** —— `gh auth login` 需用户本人在浏览器完成授权，
  任何脚本都不能代做。
- 仓库**无 `.git`、无 `.gitignore`**：干净起步，没有历史需要洗，
  也不存在「曾经提交过敏感文件」的隐患。

**目录体量（决定忽略清单的底线）**：

| 目录 | 文件数 | 体积 | 性质 |
|---|---|---|---|
| `app/node_modules` | 7942 | 477 MB | 可再生，`package-lock.json` 已锁定版本 |
| `dist/` | 80 | 585 MB | 打包产物（exe/dll/pak），可再生 |
| `数据/` | 36 | 2.2 MB | **运行时状态**：库、照片、每日快照、回收站 |
| `数据底稿/` | 5 | 20 KB | 录入草稿（当前是虚构示例） |
| 其余全部（源码/文档/openspec） | — | ≈1 MB | 应跟踪 |

**绝对路径清点**（`grep 族谱pc端项目`，全文 28 处，分四类）：

| 位置 | 内容 | 处置 |
|---|---|---|
| `app/package.json:44` | `directories.output: "D:\\族谱pc端项目\\dist"` | **本次改为 `../dist`** |
| `app/electron/paths.js:23` | `DEFAULT_DATA_DIR = 'D:\\族谱pc端项目\\数据'` | 不动（见 D3） |
| `app/scripts/verify-asar.js:19-20` | 校验脚本指向本机 `程序\` 与 `dist\` | 不动（见 D3） |
| 注释与文档（`main.js`、`store.js`、`README.md`、`installer.nsh` 注释、测试断言） | 描述数据/产物落点 | 不动，纯文字，不影响 clone |

## Goals / Non-Goals

**Goals:**

- 忽略清单让「装依赖 → 跑应用 → 打包 → 录数据」整套本地工作流之后，
  `git status` 只剩源码与文档变更。
- 本机行为零变化：产物仍落 `D:\族谱pc端项目\dist\`，数据目录解析逻辑不动。
- 远端私有；「转公开」成为一个有明确触发条件的显式决策，而非顺手动作。

**Non-Goals:**

- 不做数据脱敏（示例数据是虚构的，用户 2026-10-21 确认）。
- 不改 `DEFAULT_DATA_DIR`、不改 `verify-asar.js`、不动 `installer.nsh`。
- 不补 `LICENSE` / `repository` 字段 / README 徽章 —— 转公开时再补。
- 不建 CI、不加 git hooks（测试已由 `npm test` 覆盖，私有测试阶段不加机制）。

## Decisions

### D1 — 忽略清单按「性质」分六组，不按目录罗列

```
app/node_modules/     # 第三方依赖，可再生
dist/                 # 打包产物，可再生
数据/                  # 运行时状态：库/照片/快照/回收站，将来必沉淀真实数据
数据底稿/              # 录入草稿，将来可能放真实数据
*.log                 # 运行日志（boot.log 等在 数据/ 内，双保险）
*.bak / *.migrated-*  # 库备份与迁移原件
```

**理由（关键是中间两组，与「示例数据真假」无关）**：`数据/` 被排除不是因为它现在敏感，
而是因为它是**运行时状态** —— 用户README 的下一步建议就是「拿真实数据试跑」，
一旦录了真数据，这个目录就必须已在忽略清单里。`数据底稿/` 同理：目录定位是草稿，
保不齐以后往里放真底稿，tracked 了容易误提交。**按性质排除比按内容判断可靠** ——
内容会变，性质不会。

**考虑过的替代**：把 `数据底稿/` 收进仓库（当前是虚构示例，20KB 无所谓）——
否。目录名叫「底稿」就是在提示它会变，现在收进去等于给将来埋钩子。

### D2 — 私有先行，转公开是一个有触发条件的决策

先私有（`gh repo create --private`），用户测试效果后再定公开与否。

**转公开的前置认知已记录在案**：示例数据虚构 → 转公开时**无需脱敏**，
只剩常规卫生项（提交邮箱暴露、LICENSE、`repository` 字段）。
其中提交邮箱（QQ 邮箱）是唯一真实的个人信息暴露面，私有阶段仅协作者可见。

**考虑过的替代**：直接公开 —— 否。用户明确说「先测试测试效果」，
且未登录的 gh 账号在授权前，可见性选择随时可改，没有理由赌。

### D3 — 只相对化 `package.json` 的 output，其余绝对路径原地不动

`"D:\\族谱pc端项目\\dist"` → `"../dist"`。electron-builder 把相对输出路径
解析到工程目录（`app/`）的上一级，即仓库根 —— **解析结果与原来的绝对路径逐字节相同**，
本机打包行为不变，但 clone 到无 D 盘的机器上也能构建。

**为什么不顺带改另外两处**：

- `paths.js` 的 `DEFAULT_DATA_DIR`：这是**产品行为**，且有 `D:\族谱pc端项目\数据`
  → `C:\Users\<用户>\族谱数据` → Electron `userData` 三级 fallback（`tests/db.test.js:75`
  专门守着「有 D 盘时优先 D 盘」）。它在新机器上会自动建目录、能工作，
  **不是缺陷**；改它是产品决策，不搭建仓的车。
- `verify-asar.js` 的硬编码路径：本地 asar 校验脚本，校验的是作者机器上
  「已安装版 vs 打包版」的 asar 一致性，clone 上没有对应文件，跑了反而报错。
  留着不动是对的方向。

### D4 — 仓库名暂定 `family-tree`

取自 `app/package.json` 的 `name`。推送前可改；改名只影响远端 URL，
本地 `.git` 不受影响。用户名未知（gh 未登录），`repository` 字段因此也留到建仓后、
转公开前再补 —— 现在补等于猜。

## Risks / Trade-offs

- **[暂存区核对遗漏，把 585MB 的 dist 或数据目录提交进去]** → 双重防线：
  ① `git add .` 后先跑 `git status` 人工核对清单再 commit；② 推送完成后在
  GitHub 网页扫一眼文件树。spec 的「四类非源码资产均被忽略」场景即验收标准。
- **[误推公开]** → `gh repo create` 显式带 `--private`，不依赖默认值；
  spec requirement 3 把这个决策固化成不变量。
- **[QQ 邮箱随提交暴露]** → 私有阶段仅协作者可见；转公开前换成 GitHub
  noreply 邮箱（只改本仓库级配置，不动全局）。
- **[`.gitignore` 将来被误删一行，数据混进提交]** → 缓解：忽略规则按性质分组、
  每条带注释说明「为什么」；回归时可跑 spec 的忽略检查场景（`git check-ignore`）。
  不加 hook 强制执行（Non-Goal），私有阶段靠人眼 + 规范。
- **[相对路径写错导致产物跑飞]** → `../dist` 的解析结果与旧绝对路径相同，
  且 tasks 里有「读回确认 + 本机打包验证」一步；真跑飞了改回一行就是，
  回滚成本接近零。

## Migration Plan

无数据迁移、无配置开关、无依赖变更。

**部署顺序**：建 `.gitignore` → `git init` → 核对暂存区 → 首次提交（中文注释）→
`gh auth login`（用户操作）→ `gh repo create family-tree --private --source=. --push`
→ 网页核对。

**回滚**：删远端仓库（GitHub 网页设置页）+ 删本地 `.git` 目录。历史只有一条提交，
删了无损失；`.gitignore` 与 `package.json` 改动各自独立可弃。

## Open Questions

- **仓库名**：暂定 `family-tree`，推送前用户可改（改名的唯一成本是远端 URL）。
- **是否实跑一次 `npm run dist` 验证产物路径**：默认验证到「读回配置 + 解析结果相同」
  为止；本机 EPERM 是打包已知问题（见 README/项目记忆），实跑由用户按需决定。
