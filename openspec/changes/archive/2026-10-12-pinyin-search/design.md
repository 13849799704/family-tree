# Design

## Context

搜索逻辑现在整段住在 `app/src/app.js` 的 `collectSearchHits()`（约 1409 行起）：读 `state.dataset`、`state.kinship`、`state.layouts`，返回排好序的命中数组；再由 `renderSearchMenu()` 渲染成浮层。**它一行都测不到** —— 依赖 `document` 与全局 `state`，跑不进 `tests/run.js`。

约束（来自项目既有约定，不是本文新增）：

- `app/src/core/*` **零 DOM、零 npm 依赖**，因此能在 Node 里直接单测；`tests/run.js` 是它的回归网。
- 「未覆盖不猜」是铁律：匹配不到就如实说不知道，不编。
- 运行时依赖只有 `html2canvas` + `sql.js`，打包时 `asar` 体积敏感（曾从 20.64 MB 砍到 0.32 MB）。
- 拼音只服务**姓名**；称谓是本地口语词，不参与拼音。

## Goals / Non-Goals

**Goals:**

- 让「谁命中、怎么排序」成为可在 Node 里单测的纯函数，并为此后的搜索改动兜住回归。
- 拼音表**运行时零依赖**：不为一张表引几百 KB 的 npm 包。
- 拼音候选串在一次扫描里同时支持首字母与全拼，不做两套匹配逻辑。

**Non-Goals:**

- 不做「中间省略」匹配（`lming` 找「李明」）—— 口径要可解释，宁可搜不到也不猜省略位置。
- 不给称谓做拼音。
- 不动数据模型与数据库结构（搜索是纯查询）。
- 不重写结果浮层的交互（上下键、回车、滚动位置保持等行为沿用现状）。

## Decisions

### D1 · 匹配逻辑下沉到 `core/search.js`，DOM 相关的留在 `app.js`

**选**：新增 `core/search.js`，对外是纯函数 —— 输入 `people[]`（已规范化的 person）、`kinship` Map、查询串、以及由调用方传入的「这个人属于哪一页」（`null` / `'main'` / 姻亲 key），输出排好序的命中数组。`app.js` 保留 `searchScopeOf()`（依赖 `state.layouts`）与全部渲染。

**理由**：项目最看重的一条是「core 能单测」。作用域判定绑在布局上，进不了 core；但「拼音匹不匹配」「命中途径是谁」「谁排前面」是纯逻辑，必须能测。

**备选**：整段留在 `app.js`、靠 e2e 覆盖 —— 否决。搜索是天天用的路径，而 e2e 跑一次要开真 Electron 窗口，反馈太慢，这类纯逻辑回归恰恰最适合跑在毫秒级的单测里。

### D2 · 一张「字 → 全拼」表，首字母由它派生

**选**：静态表 `core/data/pinyin.js`，形如 `{ "李": ["li"], "长": ["chang","zhang"] }`。首字母 = 拼音串第 0 个字符，不另存一张表。

```
李明 → 全拼 "liming"          首字母 "l" + "m" = "lm"
李长 → 全拼 {"lichang","lizhang"}   首字母 {"lc","lz"}
```

**理由**：一张表搞定两种形态，表体积省一半，多音字也只是同一 key 下多一个元素。30 个字 × 最多 2 音 = 最多 60 个候选串，全谱几百人的匹配成本可以忽略。

**备选**：两张表（首字母表 + 全拼表）—— 否决，首字母完全可派生，存两份等于给自己制造「两张表不一致」的新可能。

### D3 · 表在开发期生成、产物提交进仓库

**选**：`app/scripts/gen-pinyin-table.js` 从权威数据源（Unicode Unihan 的 `kMandarin` 字段；备选 GB2312 码表对照）取「通用规范汉字表一级字（3500 个）」，输出静态表进 `core/data/pinyin.js`。生成脚本只跑一次，产物 commit，运行时不再需要数据源。

**理由**：本机打包必须走 `node_modules/electron/dist` 那条路（Windows Defender 会卡 rename），依赖越少越好；而且 `build.files` 已经为砍体积写了一大串 `!` 排除规则，不值得为搜索再加一个运行期依赖。开发期依赖数据源、运行时依赖仓库 —— 两头都不亏。

**备选**：运行时引 `pinyin-pro` —— 否决，破坏 core 零依赖，且几百 KB 换一张 20 KB 表不划算。

**未定的细节（可在 tasks 阶段定，不影响 spec）**：字表存储方式（按码位排序的并行字符串，还是普通对象字面量）、生成脚本是一次性手跑还是留成可重跑的 npm script。倾向前者简单、后者可复现。

### D4 · 生僻字整条退出，不跳字

**选**：姓名里只要有一个字查不到拼音，该人整条不参与拼音匹配 —— 不是「跳过那个字、把其余字拼起来」。

**理由**：跳字会拼出「李龘」→ `li` 这样的串，于是搜 `li` 把「李」和「李龘」一起捞出来，用户以为搜对了，实际上是把两个人混成一个。这正是「未覆盖不猜」要挡的那类错。这类人仍可用汉字子串搜到，能力没丢。

### D5 · 拼音全等不开列表

**选**：直接跳转的条件**仍然只有**「姓名全等且唯一」。`liming` 恰好唯一命中，照样开列表。

**理由**：两条。一是拼音全等的「唯一性」没姓名全等硬 —— `liming` 还可能是「黎明」「李铭」；二是 v0.2.55 用户已经拍过一次板：宁可让人挑，不要替用户挑人。「拼音只是另一种找人的方式，不是新的快捷方式」这条口径保持一致，用户不用记两套规则。

### D6 · 排序只改第 2 条

**选**：`主树 > 姻亲 > 游离` → `姓名 > 拼音 > 称谓` → `生年早的在前` → `无生年的最后`。

**理由**：拼音是「确定的姓名」，比模糊的称谓强，但弱于姓名原文命中（原文命中说明用户已经知道确切写法）。第 3、4 条不动 —— 族里按长幼认人，把没录生日的人往前塞，排出来的顺序就是错的。

**⚠️ 实现时撞出来的真相：三种命中途径互斥，这一档平时观察不到。**

```
姓名命中   要查询串是姓名的「汉字」子串
拼音命中   要查询串是「拉丁字母」且含在 liming / lcs 这类候选串里
称谓命中   要查询串是称谓的「汉字」子串
                    |
  同一个查询串不可能同时满足两条 → 三种途径永不同时出现在一份结果里
```

也就是说排序第 2 条里的「拼音」那一档，**在族谱数据下永远不会和另两档相遇**（唯一例外是有人起拉丁名，如 `David 李`）。**仍然保留三档**：它无害、自解释，且一旦将来支持拉丁名或拼音称谓就立刻生效。`tests/run.js` 里钉的是**能观察到的事实**（拉丁查询只出拼音命中 / 中文查询不出拼音命中），不是这条排不到的顺序。

### D7 · 拼音命中行展示命中的拼音串

**选**：结果行里姓名照旧，右侧（弱化样式）补上命中的那一个拼音串，如 `李明  liming`。

**理由**：汉字没法标黄出「是哪一段匹配上的」（`lming` 在「李明」里没有任何连续片段）。不标的话用户会怀疑「到底搜到了没有」；标一个弱化的拼音串，等于把匹配过程摊开给他看。用弱化样式而不是高亮，是因为匹配行为本身**不是**用户要找的重点。

**备选**：拼音命中行整行标黄 —— 否决，会让「我只是碰巧搜到」看起来像「这是重点推荐」。

## Risks / Trade-offs

- **[一级字表覆盖不到的生僻字姓名直接失去拼音可搜性]** → 用汉字子串兜底（D4），输入框提示里只承诺首字母 / 全拼两种形态，不宣传「所有字都支持」。
- **[多音字只取前两个读音，仍会漏]** → 人名里的多音字绝大多数是双音；漏的那部分仍可汉字搜到。取舍是「表小 + 行为可预测」优于「表大 + 行为说不清」。
- **[生成脚本是一次性的，表错了只能重跑]** → 表是静态数据、diff 清晰，真错了改脚本重跑即可；脚本与数据源出处一起写进表头注释。
- **[搜索逻辑从 app.js 搬到 core，行为可能悄悄变]** → 搬迁前后必须逐条对拍现有行为（尤其排序第 3/4 条，以及「姓名为空时 `displayName` 返回『未知』」这类边角），把对拍结果作为回归基线，而不是靠肉眼 review diff。
- **[把搜索纳入单测后，`tests/run.js` 继续变大]** → 现状 94 项，加一组约十几项仍在可接受范围；不为它单独拆测试文件，保持「core 一套跑完」的习惯。

## Migration Plan

无数据迁移。回滚 = 删掉 `core/search.js` + `core/data/pinyin.js`，把 `app.js` 里那几行改回内联实现。
